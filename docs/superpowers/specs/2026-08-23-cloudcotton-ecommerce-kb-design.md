# 云棉家居电商售后知识库改造 — 设计文档（Spec）

## 1. 背景与目标

### 1.1 为什么改

当前项目是一个**工程质量很高但定位悬浮**的企业 RAG 模板：

| 已有资产（保留不动） | 问题 |
|---|---|
| LangGraph Agentic RAG（检索即工具） | README 定位是泛泛的"企业知识库模板"，说不出解决谁的什么问题 |
| PostgreSQL + pgvector + Redis 缓存 | 「电商售后」只散落在 1 个测试文件和 1 个 demo 文档里 |
| 租户隔离 / JWT / PII 脱敏 / 审计 | **没有任何评测体系**——检索好不好、答得对不对，全靠感觉 |
| 无证据强制拒答 + 人工转派闭环 | 679 行的云棉家居知识库是单一大文件，检索粒度和来源展示都不理想 |
| 用户反馈（赞/踩）+ 审批率统计 | 前端引导文案与业务场景无关 |
| 119 个后端测试全过、CI 三件套 | |

### 1.2 改造后的一句话定位

> **面向跨境电商（云棉家居 CloudCotton Home）的售后智能客服知识库**：客服/运营上传内部知识文档，一线客服用自然语言查询退换货、物流、支付等政策，系统保证**有据可依、无据拒答、来源可溯、效果可测**。

面试故事从"我搭了一个 RAG 模板"升级为：
"我把一个生产级 RAG 系统（租户隔离、审计、拒答机制）落到**具体业务**（跨境家居电商售后），并建立了**黄金评测集 + 检索命中率/回答质量评估体系**，用实测数据驱动迭代。"

### 1.3 成功标准（可验证）

1. 全部既有测试保持通过（119 后端 + 35 前端）
2. 知识库达到真实产品体量：**12 个主题文档、3500+ 行、500–800 chunk**
3. 新增黄金评测集 **120 题**（L1 直查 / L2 口语改写 / L3 多跳推理 三层 + OOS 拒答），附出题校验脚本
4. 评测脚本可一键运行并输出报告；检索评测在真实 pgvector + 百炼 embedding 上跑出**实测数字**写入 README（目标 hit@5 ≥ 0.90，以实测为准，不编造）
5. 拆分后的主题文档通过现有 `/documents/upload` 链路导入成功
6. README / 前端文案对齐电商场景

### 1.4 「真实产品」判据（与玩具 demo 的区别）

| 维度 | 玩具 demo | 本项目目标 |
|---|---|---|
| 语料规模 | 1 文件几百行，检索无区分度 | 12 文档 3500+ 行，干扰项密度真实 |
| 评测集 | 无，或十几题自问自答 | 120 题、三层难度、逐题标注依据、可校验 |
| 指标 | "效果不错" | hit@k / MRR / 分层通过率，实测落 README |
| 运维故事 | 能跑 | 干扰密度下的检索调优记录（词典迭代前后对比） |

## 3. 详细设计

### 3.1 知识语料重组（真实产品标准）

**规模目标：从 1 个文件 / 约 700 行，扩到 12 个文档 / 约 3500+ 行 / 预计 500–800 个 chunk**（chunk_size=800, overlap=100），达到一个真实中型跨境电商知识库的量级——这个体量下检索质量差异才显现得出来，评测才有意义。

```text
docs/demo_data/cloudcotton/
├── 01-公司概况与品牌认证.md        ← 原「一」扩写（+发展历程、组织架构、认证清单表）
├── 02-产品目录与SKU规则.md         ← 原「二」扩写
├── 03-尺寸规格对照.md              ← 原「三」扩写（+儿童尺寸、枕头被芯尺寸、误差说明）
├── 04-材质详解与性能对比.md        ← 原「四」扩写（+材质横向对比表、选购建议、认证关联）
├── 05-洗涤护理指南.md              ← 原「五」扩写
├── 06-物流配送政策.md              ← 原「六」扩写（+加拿大/墨西哥线路、旺季时效表、清关说明）
├── 07-退换货与退款政策.md          ← 原「七」扩写（+换货流程步骤化、部分退款情形）
├── 08-支付货币与发票.md            ← 原「八」扩写（+各市场本地支付方式、拒付(chargeback)处理）
├── 09-促销积分与礼品卡.md          ← 原「九」扩写（+会员等级、黑五历史折扣参考）
├── 10-客户服务与FAQ.md             ← 原「十」扩写（FAQ 从 11 条扩到 25+ 条）
├── 11-B2B批发与企业采购.md         ← 原「十一」扩写（+样品政策、物流条款Incoterms、合规文件）
├── 12-投诉处理与赔偿标准.md        ← 原「十五」独立成文（客服 SOP 视角，含话术要点）
└── （原十三「可持续发展」并入01；十四「市场合规」并入08；十六「技术FAQ」拆入05和10）
```

**内容纪律（防编造）：**
- 扩写只允许两类内容：① 把原文一笔带过的点展开成结构化表格/流程（如换货流程步骤化）；② 补充行业通用常识性内容并保持内部一致性（如 Incoterms 解释）
- 所有数字（价格、天数、比例）必须与原知识库一致或显式标注为示例；新增数字须自洽（如会员等级折扣与促销章节不打架）
- 每个文档开头加导语（"本文档供 XX 团队查询 XX 使用"），结尾加版本行

**为什么值得做大**：评测集 60→120 题需要足够的干扰项密度——文档太少时随便检索都能命中，hit@5 区分度是假的；3000+ 行语料下"检索到正确文档"才是一个真实的排序问题。这是"真实产品"与"玩具 demo"的分界线。

理由：来源归因更清晰——前端 SourceCard 会显示"参考了《退换货与退款政策》"，演示效果和评测的 expected_doc 判定都依赖这个。

### 3.2 黄金评测集 `evals/golden_set.jsonl`

JSONL 格式，每行一题：

```json
{"id": "RT-001", "category": "退换货", "question": "独立站买的四件套签收后还能无理由退货吗？", "expected_doc": "05-售后与退换货政策", "expected_keywords": ["7", "吊牌"], "should_refuse": false}
{"id": "OOS-001", "category": "拒答测试", "question": "你们公司的竞品 Sleep Number 的床垫多少钱？", "expected_doc": null, "expected_keywords": [], "should_refuse": true}
```

字段说明：
- `id`：类别前缀 + 序号（RT=退换货 LG=物流 PAY=支付 PROMO=促销 PROD=产品 CARE=护理 B2B COMP=合规 OOS=拒答）
- `expected_doc`：期望命中的文档名前缀（检索评测判定用）；拒答题为 null
- `expected_keywords`：答案必须覆盖的关键词（≥1 个即算过；端到端评测用）
- `should_refuse`：true 时要求系统拒答（无证据拒答机制的正确性验证）

题目分布（共 **120 题**，与 3500 行语料的干扰密度匹配）：

| 类别 | 数量 | 示例 |
|---|---|---|
| RT 退换货退款 | 22 | 亚马逊买的怎么退？换货流程几步？部分退款什么情形？拒付(chargeback)怎么办？ |
| LG 物流配送 | 16 | 发美国用什么快递？偏远地区附加费？PO Box 能寄吗？黑五期间时效？ |
| PAY 支付发票 | 12 | 支持分期吗？日元结算有手续费吗？欧盟开发票含 VAT 吗？Klarna 逾期？ |
| PROMO 促销积分 | 14 | CloudCoins 怎么攒怎么花？折扣码能叠加吗？会员等级权益？生日优惠？ |
| PROD 产品SKU | 20 | 云奢系列是什么棉？CL-SET4-WT-QN 是什么产品？儿童系列认证？羽绒被蓬松度？ |
| CARE 洗护 | 12 | 天丝四件套能机洗吗？羽绒被怎么存？毛巾 700GSM 怎么护理？枕芯多久换？ |
| B2B 批发 | 10 | 酒店批量采购折扣梯度？样品政策？Net 30 账期条件？定制交期？ |
| COMP 合规认证 | 6 | OEKO-TEX 证书编号？欧盟 GPSR 要求？美国 FTC 纺织标签？ |
| CS 客服流程 | 8 | 投诉多久响应？升级投诉邮箱？负面评价能删吗？赔偿标准表？ |

**出题分层（真实产品评测的关键设计）**：
- **L1 直查题（约 40%）**：问题措辞与文档原文高度一致——验证基线召回
- **L2 口语改写题（约 35%）**：用户口语 vs 书面文档（"买错了想退钱" vs "退货政策"）——验证同义词典 + embedding 泛化
- **L3 多跳/约束题（约 25%）**：需要跨段落综合（"我 11 月 28 日下单、12 月 5 日还没到，按政策算延误了吗？"）——验证 Agent 检索策略与推理
- **OOS 拒答题 10 题单列**（不计入上表）：竞品价格 / 编造的产品系列 / 实时库存 / 法律建议等

出题纪律：**每一题的答案必须能在对应主题文档中找到原文依据**，出题时标注原文行号（写在评测集维护说明里，不入 JSONL）。拒答题必须是知识库确实不涵盖的。

### 3.3 检索评测脚本 `scripts/evaluate_retrieval.py`

职责：只评检索层（rewrite → embed → pgvector top-k → distance 过滤），不调 LLM。

```text
用法：
  python scripts/evaluate_retrieval.py --golden evals/golden_set.jsonl \
      [--k 5] [--tenant-id cloudcotton] [--report evals/reports/retrieval-<date>.md]

流程：
  对每题：
    q = rewrite_query(question)                    # 复用现有规则改写
    results = pgvector_similarity_search_with_score(q, k, tenant_id)
    hits = [r for r in results if r.distance <= MAX_DISTANCE]
    hit@i = hits 中前 i 个里出现 expected_doc 前缀匹配
  输出：
    hit@1 / hit@3 / hit@5（总体 + 分类别）
    MRR（mean reciprocal rank）
    平均检索延迟 p50/p95
    未命中题目清单（题号 + 检索到的 top5 来源 + 各自 distance）← 迭代抓手
```

两种运行模式：
- **真实模式**（默认）：连 `.env` 的百炼 embedding + Postgres，需要先导入语料。产出 README 引用的实测数字。
- **CI 安全单测**：指标计算函数抽成纯函数放 `app/core/eval_metrics.py`，`tests/test_evaluation.py` 用构造数据测 hit/MRR/分类聚合的正确性，不碰网络。

### 3.4 端到端问答评测 `scripts/evaluate_qa.py`

职责：走完整 `/qa/ask` 链路（含 Agent 决策、拒答、引用），评最终答案质量。

```text
用法：
  python scripts/evaluate_qa.py --golden evals/golden_set.jsonl \
      --base-url http://127.0.0.1:8765 --token <JWT> \
      [--limit 20] [--level L2,L3] [--category RT,LG] [--report ...]

判定规则（每题）：
  ① 拒答正确性：response.refused == should_refuse
  ② 关键词覆盖：非拒答题，answer 中命中 ≥1 个 expected_keywords
  ③ 来源一致性：非拒答题，sources 里存在 expected_doc 前缀匹配
输出：
  通过率（三关全过）、各单项通过率、分类别矩阵、**分层矩阵（L1/L2/L3 各自通过率）**
  失败题明细（问题/回答/来源/原因标签）、报告同时落 markdown + json（json 供后续对比趋势）
```

注意：此脚本消耗真实百炼 token，明确标注为**手动触发**。成本估算（真实数字，跑完填 README）：120 题 × 约 2K–4K token/题 ≈ 单轮全量 ¥1–3 量级（qwen-turbo/qwen-plus 档）；支持 `--limit` / `--level` / `--category` 分片跑，CI 不跑它。

### 3.7 明确不做（YAGNI）

- ❌ 不引入 Reranker 模型（当前 TOP_K=5 + distance 阈值够用；若实测 hit@3 低再议，属于后续迭代项）
- ❌ 不做多轮对话评测（首轮命中率是主要指标；多轮记忆已有单测覆盖）
- ❌ 不动 ingest 分块策略、不动审计/预算/隔离任何安全机制
- ❌ 不做自动化 LLM-as-judge 打分（关键词+拒答+来源三关已可量化，judge 反而引入不可复现性）
- ❌ 不新增 Python 依赖（评测脚本只用标准库 + 现有 httpx/sqlalchemy）

## 4. 任务分解概览（供实施计划展开）

1. **语料工程**：拆分+扩写 → cloudcotton/ 12 文档 3500+ 行（最大工作量项，纯文档）
2. **黄金评测集**：120 题（L1/L2/L3 分层 + OOS 拒答），逐题标注文档依据
3. `app/core/eval_metrics.py` 纯函数 + `tests/test_evaluation.py` 单测（TDD，含分层聚合）
4. `scripts/evaluate_retrieval.py`（真实模式 + 报告落盘）
5. `scripts/evaluate_qa.py`（三关判定 + 分层矩阵 + 分片参数）
6. 同义词典扩充至 40+ 词条组 + 单测
7. 导入语料跑真实检索评测 → 迭代词典/语料直至 hit@5 达标 → 记录实测数字
8. QA 端到端评测分片跑（先 L1 子集验证链路，再全量）→ 记录实测数字
9. README 改写（填实测数字、业务场景、评测体系说明）+ 前端文案
10. 全量回归（pytest + vitest + tsc）→ commit/push

**工作量分布提示**：任务 1+2 占总工作量约 60%（写语料和出题），3–6 是确定性编码，7–8 是跑数迭代。语料扩写由子代理并行分工（按文档主题切给多个 agent），出题在语料定稿后做。

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| 百炼 embedding 对中文长尾口语召回差 → hit@5 不达标 | 评测报告自带未命中清单，优先调同义词典而非改核心代码；仍不行则在计划外提 reranker 议题 |
| 扩写语料引入内部矛盾（新表格与旧政策数字冲突） | 语料定稿前跑一遍一致性自查清单（价格表/时效表逐项对照原文档）；评测出题时发现矛盾即修语料 |
| L3 多跳题判定主观（关键词覆盖不了推理题） | L3 题的 expected_keywords 选"结论性数字"（如延误补偿金额），不选过程描述 |
| 真实评测烧 token | 检索评测只耗 embedding（极便宜）；QA 评测支持 --limit/--level/--category 分片，默认手动触发 |
